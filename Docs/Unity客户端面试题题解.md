# Unity 客户端面试题与参考答案

本文按知识领域将题目分为 C# 与 Unity 两部分，题号在各部分内独立编号。答案以 Unity 客户端岗位的常见追问深度编写；实际面试中应结合项目经历说明使用场景与取舍。

## 一、C# 基础与进阶

### 1. `class` 和 `struct` 的区别是什么？

**答案：**`class` 是引用类型，变量保存对象引用，实例通常分配在托管堆上；赋值或传参默认复制引用。`struct` 是值类型，变量保存实际数据，赋值或传参默认复制整个值；它可内联在局部变量、数组元素或包含它的对象中，并不等于“永远在栈上”。

结构体适合小、无引用、语义上像数值的数据，例如坐标和颜色。避免把大结构体频繁按值传递，必要时使用 `in` / `ref`；也避免可变结构体，因为复制后容易产生难以发现的状态错误。结构体装箱为 `object` 或接口时会产生 GC 分配。

### 2. 值传递、引用传递与 `ref` / `out` / `in` 分别是什么？

**答案：**C# 默认都是按值传递：值类型复制数据，引用类型复制引用，因此在方法内修改引用对象的成员会影响原对象，但给形参重新赋值不会改变调用方变量。

- `ref`：传入变量本身，可读写，调用前必须已赋值。
- `out`：传入变量本身，方法必须赋值，调用前可不赋值。
- `in`：按只读引用传递，常用于避免复制较大的只读结构体。

`ref` 参数会增加别名关系，除非确有性能或 API 语义需求，不应滥用。

### 3. 装箱和拆箱是什么？有什么性能影响？

**答案：**将值类型转换为 `object`、接口或其他引用类型时会装箱：运行时在托管堆创建对象并复制值。将该对象再显式转换回对应值类型是拆箱。装箱会制造 GC 压力，拆箱还要求类型完全匹配，否则抛异常。

在 Unity 的高频路径中，常见来源有把 `int`、`enum` 传给 `object` 参数，非泛型集合，以及值类型调用接口。应优先使用泛型集合、泛型 API，并用 Profiler 验证分配来源。

### 4. `string` 为什么不可变？字符串拼接怎样优化？

**答案：**`string` 不可变意味着任何“修改”都会创建新字符串。这样有利于安全共享、哈希和线程安全，但在循环中使用 `+=` 会反复分配与复制字符，复杂度可能退化为平方级。

已知会多次拼接时用 `StringBuilder`；格式化少量内容时可用插值或 `string.Concat`。Unity UI 的逐帧文本更新也会造成 GC 和字体重建，应只在显示内容实际变化时更新，或采用 TMP 的无分配格式化接口。

### 5. `var`、`dynamic` 和 `object` 的区别？

**答案：**`var` 是编译期类型推断，变量的静态类型在编译后已确定，不降低类型安全。`object` 是所有类型的基类，调用成员通常需要转换；值类型赋给它会装箱。`dynamic` 将成员绑定推迟到运行时，调用失败会在运行时抛异常，并有额外开销。

游戏业务代码通常使用显式类型或 `var`；除与动态语言、反射结果互操作外，不建议使用 `dynamic`。

### 6. 委托、事件和 `Action` / `Func` 有什么关系？

**答案：**委托是保存方法引用的类型，可组合多个回调。`Action` 和 `Func` 是框架提供的通用委托：`Action` 无返回值，`Func` 最后一个泛型参数是返回值。`event` 是对委托的封装，外部只能订阅和取消订阅，只有声明类能触发它，因此更适合公开通知。

订阅者生命周期短于发布者时必须取消订阅，否则发布者会持有订阅者，造成对象无法回收或场景切换后的无效回调。在 Unity 中常在 `OnEnable` 订阅、`OnDisable` 取消订阅。

### 7. 闭包是什么？使用 Lambda 时有什么坑？

**答案：**Lambda 捕获外部局部变量时，编译器会生成闭包对象，使该变量在方法返回后仍可存活。它便于回调写法，但可能产生额外分配，也可能意外延长对象生命周期。

循环中捕获变量要确认捕获的是每次迭代的独立变量；移除监听时，重新写一个相同 Lambda 通常无法匹配原委托，应保存委托实例。Update 等高频路径避免创建捕获 Lambda。

### 8. `IEnumerable`、`ICollection`、`IList` 和 `List<T>` 如何选择？

**答案：**`IEnumerable<T>` 仅表达可枚举，适合只读遍历接口；`ICollection<T>` 增加数量和增删；`IList<T>` 增加索引访问和插入；`List<T>` 是基于连续数组的具体实现，按索引访问快，尾部追加摊销为 O(1)，中间插入或删除为 O(n)。

对外暴露应选择满足需求的最小接口，避免调用方依赖具体容器。若需要按键查询选 `Dictionary<TKey, TValue>`；频繁头尾操作可考虑队列或链表，但应以实际访问模式和 Profiling 为准。

### 9. `Dictionary` 的原理和注意事项是什么？

**答案：**字典通过键的哈希值定位桶，再用 `Equals` 区分哈希冲突，平均查找、插入和删除为 O(1)，冲突严重时会退化。键在作为键期间必须保持哈希值与相等性不变；可变对象作为键后修改参与哈希的字段，会导致无法正确查找。

初始化时预估容量可减少扩容和重哈希。遍历时不能修改同一个字典；如需删除，可先收集键或使用其他策略。字符串键会有哈希与比较开销，性能敏感场景可使用整数 ID 或枚举。

### 10. `foreach` 和 `for` 的性能差异需要如何看待？

**答案：**不能一概而论。对数组和 `List<T>`，现代 C# 的 `foreach` 通常使用结构体枚举器，性能接近 `for`，可读性更好。若枚举接口类型、非泛型集合，或使用 LINQ 链式查询，可能发生装箱、枚举器分配或额外遍历。

性能敏感代码先使用 Profiler 验证。需要索引、倒序删除或避免枚举器时用 `for`；普通遍历不应为了微小差异牺牲清晰度。

### 11. LINQ 在 Unity 中有哪些优缺点？

**答案：**LINQ 表达筛选、映射和聚合很清晰，适合编辑器工具、低频业务和初始化代码。但许多操作会创建枚举器、迭代器对象、闭包或中间集合，`ToList`、`OrderBy` 等还会分配并遍历数据。

不要在 `Update`、战斗循环等热路径中无意识使用 LINQ。可改为缓存结果、手写循环或复用容器；是否优化应由 Profiler 的 GC Alloc 与 CPU 数据决定。

### 12. `async` / `await` 的执行模型是什么？在 Unity 中如何使用？

**答案：**`async` 方法会被编译为状态机；遇到未完成的 `await` 时保存状态并返回，任务完成后继续执行后续逻辑。它不等于自动开新线程：是否切线程取决于被等待的操作及同步上下文。

Unity 的对象 API 绝大多数只能在主线程调用。可将纯计算放到后台线程，完成后切回主线程再操作 Unity 对象；网络、资源加载可使用 Unity 的异步 API、协程或项目统一的异步封装。异步方法应支持取消、处理异常，并避免 `async void`，事件回调除外。

### 13. 协程与 `async` / `await` 的区别？

**答案：**协程由 Unity PlayerLoop 驱动，`yield return null`、`WaitForSeconds` 等表示在特定帧或条件后继续，适合帧间流程、动画节奏和 Unity 异步操作。它本身不创建线程，停止宿主 `MonoBehaviour` 或调用 `StopCoroutine` 可终止。

`async` / `await` 基于 `Task` 或其他 awaitable，更适合网络、文件、并行计算与组合等待，异常和返回值的传递也更自然。两者可在项目中并存，但要统一生命周期与取消策略，避免对象销毁后继续回调。

### 14. `Task`、线程与线程池有什么关系？

**答案：**`Task` 表示一个将来完成的操作，不等同于一个线程。I/O 任务通常不占用线程等待；`Task.Run` 才会把 CPU 工作排到线程池。线程池复用工作线程，避免频繁创建线程的高开销，但线程池任务不适合无限阻塞或长时间独占。

Unity 主线程负责渲染与大多数引擎 API。后台线程只能处理不触及 `UnityEngine.Object` 的纯数据，结果须安全地交回主线程消费。

### 15. `lock`、`Monitor`、`Interlocked` 如何选择？

**答案：**`lock` 是 `Monitor.Enter/Exit` 的语法糖，适合保护一段需要原子执行的临界区。锁对象应为私有且稳定的引用，临界区要短，避免锁内调用未知代码、等待或递归形成死锁。`Interlocked` 适合整数、引用交换和计数器等简单原子操作，开销更低，但无法替代多步骤不变式的锁。

客户端多数游戏逻辑在主线程执行；并发控制主要出现在资源加载、网络和后台计算的结果队列中。

### 16. GC 为什么会导致卡顿？常见优化手段有哪些？

**答案：**托管堆分配累积后，GC 需要扫描存活对象并回收不可达对象；在帧预算紧张时，回收工作可能造成明显帧时间尖峰。优化的重点不是“禁止 GC”，而是减少热路径的临时分配和控制对象生命周期。

常见手段包括对象池、缓存数组和列表、避免字符串拼接与 LINQ、避免装箱、预设集合容量，以及及时解除事件引用。应通过 Unity Profiler 定位 `GC.Alloc` 的真实来源，避免没有数据支撑的优化。

### 17. 什么是对象池？哪些对象适合池化？

**答案：**对象池预先创建或复用对象，使用完不销毁而是重置并归还，以减少频繁 `Instantiate` / `Destroy`、托管分配和加载开销。子弹、伤害飘字、特效、重复敌人等高频、生命周期短且可重置的对象适合池化。

池化不是无条件收益：低频对象、内存很大的对象或状态难以正确重置的对象不适合。池对象需要明确的租借、重置、归还和上限策略，并防止同一实例被重复归还或持有过期引用。

### 18. `IDisposable` 和 `using` 的作用是什么？

**答案：**`IDisposable.Dispose` 用于确定性释放非托管资源或主动释放昂贵资源，如文件句柄、网络连接和原生容器。`using` 会在作用域退出时，即使发生异常，也自动调用 `Dispose`。

它不同于 GC：GC 只管理托管内存，且回收时机不确定。Unity 的 `NativeArray`、`NativeList` 等原生容器通常必须在不再使用时 Dispose；异步 Job 依赖完成前不能释放其正在访问的数据。

### 19. `const`、`readonly` 与 `static readonly` 有什么区别？

**答案：**`const` 是编译期常量，值会直接内联到使用方，类型受限且必须在声明时赋值。公开库的 `const` 改值后，未重新编译的调用方仍可能保留旧值。`readonly` 是实例字段，只能在声明处或构造函数赋值；`static readonly` 是类级字段，在类型初始化时赋值，可以保存运行期才确定的引用或计算结果。

配置数据不应滥用 `const`；在 Unity 中常用 `static readonly` 保存不可变查表数据，但需注意域重载与初始化时机。

### 20. 什么是 SOLID？在 Unity 项目中如何落地？

**答案：**SOLID 包括单一职责、开闭原则、里氏替换、接口隔离和依赖倒置。核心目的不是增加层数，而是让变化局部化、可测试。

例如让输入、角色移动、伤害计算和 UI 展示由不同组件负责；用 `IDamageable` 表达受伤能力而非到处判断具体敌人类型；让业务逻辑依赖接口或数据定义，而不是直接依赖场景对象。对小型一次性功能保持简单，对经常扩展的战斗、任务、存档等模块再引入边界。

## 二、Unity 引擎与客户端开发

### 1. Unity 常见生命周期的调用顺序和用途？

**答案：**对象加载时通常先执行 `Awake`，随后 `OnEnable`；第一帧更新前执行 `Start`。每帧逻辑使用 `Update`，物理步使用 `FixedUpdate`，相机跟随等需要在目标更新后处理的逻辑常放在 `LateUpdate`。对象禁用时调用 `OnDisable`，销毁时调用 `OnDestroy`。

`Awake` 适合建立自身引用和内部初始状态，`Start` 适合依赖其他对象已初始化的逻辑。不要假设不同对象间 `Awake` / `Start` 的默认先后顺序；确有需求时使用 Script Execution Order 或显式初始化流程。

### 2. `Update`、`FixedUpdate` 和 `LateUpdate` 如何选择？

**答案：**`Update` 每渲染帧一次，适合输入、普通游戏逻辑和按 `Time.deltaTime` 的运动。`FixedUpdate` 按固定物理步执行，可能一帧执行多次或不执行，适合向 `Rigidbody` 施加物理力或处理物理相关状态。`LateUpdate` 在本帧所有 `Update` 后执行，常用于相机跟随和最终位置修正。

不要在 `FixedUpdate` 直接读取一次性输入，也不要把所有逻辑都塞进物理步。物理表现需要平滑时可启用 Rigidbody interpolation。

### 3. `GameObject`、`Component`、`Transform` 和 `MonoBehaviour` 的关系？

**答案：**`GameObject` 是场景中的实体容器；`Component` 是挂载在其上的能力模块；每个 GameObject 都有且仅有一个 `Transform`，保存层级、位置、旋转、缩放；`MonoBehaviour` 是可挂载 Component 的常用基类，提供 Unity 生命周期、协程等功能。

组合组件是 Unity 的基本组织方式。应让单个组件职责清晰，避免一个“上帝脚本”同时处理输入、移动、动画、战斗和 UI。

### 4. `Destroy`、`DestroyImmediate` 和 `SetActive` 的区别？

**答案：**`Destroy` 会在当前更新循环结束后销毁对象，是运行时的常规选择。`DestroyImmediate` 立即销毁，主要用于编辑器脚本；在运行时使用可能破坏正在遍历的对象结构。`SetActive(false)` 只是禁用 GameObject：对象和组件仍存在，`Update`、渲染、碰撞等会停止，重新激活可复用。

高频生成销毁对象通常使用对象池和 `SetActive`，但归还前必须重置状态、事件和协程。

### 5. `GetComponent` 的开销与优化方式？

**答案：**`GetComponent` 会在目标对象的组件列表中查找，单次通常不必过度担心，但在循环、每帧或大量对象中反复调用会累积成本。应在 `Awake`、`Start` 或依赖注入阶段缓存稳定引用；可用 `[SerializeField]` 显式绑定必要依赖，并在编辑器阶段校验。

不要为了缓存而创建难以维护的全局单例。引用可能因对象销毁、场景切换或组件替换而失效时，需要定义清楚的重新绑定时机。

### 6. Prefab、Prefab Variant 与嵌套 Prefab 的使用场景？

**答案：**Prefab 是可复用的对象模板；Variant 继承基础 Prefab 并只记录差异，适合同一类敌人、道具的外观或参数变体；嵌套 Prefab 用于把角色、武器、特效等子模块组合成更大的模板。

应让基础 Prefab 承载稳定结构，将差异放进 Variant 或数据配置。过多 Override 会让维护困难，修改基础资源前要确认是否会覆盖或影响各 Variant 的预期。

### 7. `ScriptableObject` 的优势和常见误用？

**答案：**`ScriptableObject` 是可保存为资源的 Unity 数据对象，适合角色属性、物品定义、技能配置、关卡参数等共享的静态或编辑期数据。它能减少 Prefab 上重复数据，并便于制作配置资产。

运行时不要把会随单局变化的状态直接写回资源，例如玩家当前血量或任务进度；编辑器与运行环境可能共享该实例，导致状态污染。应从定义数据创建运行时状态对象，存档也保存状态而非修改定义资产。

### 8. Unity 中如何管理场景切换与跨场景数据？

**答案：**场景切换通常使用 `SceneManager.LoadSceneAsync`，加载期间显示进度或过渡 UI，避免同步加载造成长卡顿。大型世界可使用 Additive 模式分区加载，并在卸载前处理对象引用、音频和内存。

跨场景的短期运行数据可由明确生命周期的游戏流程服务持有，或使用 `DontDestroyOnLoad` 的少量根对象；长期数据应通过存档系统序列化。关键是定义所有者和销毁时机，避免无约束的全局单例累积状态。

### 9. Addressables 解决什么问题？使用时要注意什么？

**答案：**Addressables 用地址和依赖关系管理可异步加载的资源，支持本地或远端资源、按需下载、内容更新和引用计数管理，适合资源量大或需要热更新内容的项目。

加载得到的 handle 需要在不再使用时正确 `Release`；实例化对象与加载资源的释放关系也要分清。不要把所有资源一开始全加载，也不要因过早释放仍被使用的资源导致丢失。项目应统一封装加载入口并记录所有权。

### 10. Unity 的序列化规则有哪些限制？

**答案：**Unity 默认序列化 public 字段和标有 `[SerializeField]` 的非静态字段，支持常见基础类型、Unity 对象、可序列化结构与列表。它通常不序列化属性、静态字段、字典、接口和多态引用（除非采用 `[SerializeReference]` 或自定义方案）。

序列化字段改名会丢失已有资源中的值，可用 `[FormerlySerializedAs]` 迁移。不要把运行时缓存、事件和临时状态当作 Inspector 数据；它们应在运行时初始化。

### 11. `Resources`、AssetBundle 和 Addressables 如何取舍？

**答案：**`Resources` 使用简单，但资源会被特殊打包，缺少清晰依赖与细粒度卸载控制，规模增大后不利于管理。AssetBundle 是底层资源包机制，提供灵活性但需要自行处理依赖、版本与加载策略。Addressables 建立在资源包能力之上，提供更高层的地址、依赖和异步管理。

小型原型可少量使用 `Resources`；正式项目优先采用统一的 Addressables 或资源管理方案，避免混用导致资源生命周期不可追踪。

### 12. 什么是 Draw Call？如何减少渲染开销？

**答案：**Draw Call 是 CPU 向 GPU 提交一次绘制命令的过程。数量过多会增加 CPU 提交和状态切换开销，尤其在移动端。减少方法包括共享材质、图集、SRP Batcher 兼容 Shader、GPU Instancing、静态批处理，以及合理的合批策略。

合批不是唯一指标：动态批处理有自身限制与 CPU 成本，过度合并可能增加无效绘制或内存。应结合 Frame Debugger、Profiler 和目标设备观察 Batches、SetPass、三角形数与 overdraw。

### 13. 静态批处理、动态批处理与 GPU Instancing 的区别？

**答案：**静态批处理将标记为 Static 的对象组合以减少绘制提交，适合不移动的场景物体，代价是内存与构建数据。动态批处理在运行时合并满足限制的小网格，适用范围有限，可能增加 CPU 开销。GPU Instancing 让使用同一网格和材质的一批对象通过实例数据一次或较少次数绘制，适合草、树、重复道具等。

选择前需确认材质、Shader、光照和对象变化是否满足条件，并在目标平台实测。

### 14. 什么是 overdraw？UI 如何优化？

**答案：**overdraw 指同一屏幕像素被多次绘制，透明粒子、大面积半透明 UI、层叠面板尤其容易造成 fill-rate 压力。UI 优化包括减少全屏半透明层与遮罩嵌套，拆分会频繁变化的 Canvas，复用图集与材质，避免不必要的 Layout 重建，并隐藏不可见元素。

Canvas 不是拆得越多越好：每个 Canvas 也有批次与管理成本。应让静态 UI 和高频变化 UI 分开，并用 Profiler 和 Frame Debugger 验证。

### 15. `Canvas` 的 Render Mode 有哪些？如何选择？

**答案：**`Screen Space - Overlay` 直接覆盖在屏幕上，适合 HUD 和菜单；`Screen Space - Camera` 由指定相机渲染，可控制排序并与相机关系一致；`World Space` 是场景中的平面，适合角色头顶血条、世界交互面板。

屏幕 UI 要正确配置 Canvas Scaler，通常以参考分辨率和 `Scale With Screen Size` 适配；World Space UI 要注意尺度、遮挡、相机朝向和远距离性能。

### 16. Animator 参数、状态机、Blend Tree 和 Animation Event 的使用原则？

**答案：**Animator 状态机管理离散状态转换，参数驱动条件；Blend Tree 根据速度、方向等连续值混合动画；Animation Event 可在动画的精确时间点触发脚本逻辑，例如攻击判定窗口或脚步音效。

参数应少而语义明确，避免多个脚本互相覆盖。关键战斗逻辑不能只依赖动画事件，要有状态与取消规则兜底；动画事件接收方法必须稳定，特效和音效应考虑对象池与重复触发控制。

### 17. Root Motion 是什么？何时启用？

**答案：**Root Motion 使用动画根节点的位移和旋转驱动角色 Transform，使动作中的冲刺、转身和脚步节奏更贴合动画。适合演出、近战攻击或高质量角色动作。关闭时，位移由代码、CharacterController 或 Rigidbody 驱动，动画只表现视觉。

网络同步、精确碰撞和复杂导航中需要明确运动权威，常将 Root Motion 的增量交给运动系统处理，而非让 Animator 与物理系统同时直接修改位置。

### 18. `Rigidbody`、`Collider`、`CharacterController` 如何选择？

**答案：**`Collider` 定义碰撞形状；带 `Rigidbody` 的对象参与 Unity 物理模拟，可受力、碰撞和触发；`CharacterController` 是胶囊式的运动控制组件，使用 `Move` 驱动，适合由代码精确控制的角色，不受物理力自动影响。

不要同时让 Transform、Rigidbody、NavMeshAgent 多方直接控制同一对象的位置。物理对象用 Rigidbody API；角色移动则根据玩法在 CharacterController、Rigidbody 或自定义运动控制中选定唯一权威。

### 19. `OnCollision` 与 `OnTrigger` 的区别和触发条件？

**答案：**碰撞回调用于非 Trigger Collider 的接触，如 `OnCollisionEnter`；触发器回调用于至少一个 Collider 勾选 `Is Trigger` 的重叠，如 `OnTriggerEnter`。要可靠触发，参与双方通常至少有一个带 `Rigidbody`，2D 与 3D 物理组件及回调不能混用。

触发器适合拾取、范围检测和交互区；实体碰撞适合物理接触。高频回调内避免复杂查找与分配，并用 Layer Collision Matrix 过滤不需要的检测。

### 20. 什么是 Layer、Tag 和 Sorting Layer？

**答案：**Layer 是位掩码分类，主要用于物理碰撞矩阵、射线检测和相机剔除；Tag 是字符串标识，适合少量语义分类；Sorting Layer 与 Order in Layer 控制 2D Sprite、Canvas 等的绘制前后顺序。

Layer 数量有限且是全局资源，应建立项目约定。频繁逻辑分支不要依赖字符串 Tag，可使用组件、接口或枚举表达能力和状态。

### 21. Unity Profiler、Frame Debugger 和 Memory Profiler 各用于什么？

**答案：**Profiler 用于观察 CPU、GPU、渲染、GC、物理等帧耗时与调用栈；Frame Debugger 可以逐个查看一帧的渲染事件，用于分析合批、材质切换和绘制顺序；Memory Profiler 用于查看托管堆、原生内存、资源引用和快照差异。

性能优化先在目标设备上复现，确定 CPU、GPU、内存或加载瓶颈，再针对最大热点改动，并复测帧时间与内存，而不是只看某个单一数值。

### 22. 如何定位和处理 Unity 中的内存泄漏或资源未释放？

**答案：**先用 Memory Profiler 对比进入、退出玩法前后的快照，查找不应继续存活的对象及其引用链。重点检查静态字段、事件未取消订阅、单例持有场景对象、Addressables handle 未 Release、原生容器未 Dispose，以及对象池无限增长。

处理时应修正所有权与生命周期，而不是依赖 `Resources.UnloadUnusedAssets` 强行回收。后者可能造成卡顿，且无法解决仍被引用的对象。

### 23. Unity 中常见的存档设计要点？

**答案：**将可持久化状态与静态定义分离：存档保存物品 ID、数量、角色等级、任务状态等，加载后再由 ID 查配置重建运行时对象。存档格式要有版本号与迁移策略，写入采用临时文件后替换等方式降低中断损坏风险。

不要直接序列化 `MonoBehaviour`、场景对象引用或 `ScriptableObject` 运行时实例。涉及敏感数据时可做校验、加密或服务端权威，但本地加密不能单独作为反作弊方案。

### 24. 如何设计一个可扩展的伤害系统？

**答案：**以数据和接口表达边界：攻击方生成包含来源、基础数值、伤害类型、暴击和击退等信息的 `DamageContext`；受击方通过 `IDamageable.TakeDamage` 统一处理防御、免疫、死亡和事件通知。表现层订阅结果播放飘字、音效和动画。

这样能避免武器、技能、陷阱各自直接修改血量。需要明确伤害计算的权威位置、随机数来源、无敌帧与同一攻击的命中去重，网络游戏还要区分客户端预测与服务端裁决。

### 25. Unity 客户端性能优化的一般流程是什么？

**答案：**先定义目标设备和帧预算，例如 60 FPS 对应约 16.67 ms。用真机或接近目标环境采样，判断瓶颈主要在 CPU、GPU、内存、I/O 还是加载；通过 Profiler、Frame Debugger、Memory Profiler 将问题定位到可量化的热点。

然后做最小且可验证的修改，例如减少热路径分配、降低 UI 重建、控制透明 overdraw、优化资源加载或合批。每次改动后复测性能、画面和内存，并关注副作用。优化是持续的测量闭环，不是预先堆砌“优化技巧”。
