# 摄像机与玩家操控系统迭代记录

> 用途：记录第三人称 RPG 原型中摄像机、玩家移动、锁定与动画系统的关键难点和设计取舍。可作为面试项目介绍材料，后续相关问题继续追加到本文档。
>
> 技术环境：Unity 2023.2、Cinemachine 2.10、Input System、CharacterController、Animator、QFramework Typed Event。

## 一、模块目标

实现一套同时适配键鼠和手柄的第三人称 RPG 操控系统：

- 探索状态：自由镜头、相机相对移动、角色面向实际移动方向。
- 战斗状态：保留八方向移动动画；锁定时角色面向目标。
- 锁定状态：玩家与目标尽量同框，镜头自动构图并处理障碍物遮挡。
- 相机、角色移动、动画、输入和锁定模块职责分离，后续可接入攻击、技能和 UI 状态切换。

核心实现位于：

- `Assets/Scripts/Gameplay/Character/Player/PlayerController.cs`
- `Assets/Scripts/Camera/CameraModeController.cs`
- `Assets/Scripts/Gameplay/Targeting/LockOnController.cs`
- `Assets/Scripts/Core/Input/InputManager.cs`

## 二、关键迭代与困难

### 1. 统一键鼠与手柄输入，避免玩法代码依赖具体按键

**问题**

初期移动、镜头、冲刺和锁定需要同时支持 WASD、鼠标、左/右摇杆。若在角色或相机脚本内直接读取键盘按键，后续修改键位、增加手柄或重映射都会造成逻辑分散。

**处理**

- 使用 Input System 定义 `Move`、`Look`、`Sprint`、`Equip`、`HeavyAttack`、`LockOn` 动作。
- 用 `InputManager` 作为外观/适配层：业务脚本只读取 `Move`、`Look`、`SprintHeld`，不关心输入设备和绑定路径。
- 在输入层统一处理移动死区和向量长度限制，避免手柄轻微漂移或斜向输入获得额外速度。
- 使用 `UsingGamepad` 区分鼠标 Delta 与摇杆连续值，分别提供镜头灵敏度配置。

**工程收益**

输入绑定与玩法逻辑解耦。后续增加按键重映射、UI 输入上下文或新设备时，只需扩展 Input System 配置和 `InputManager`，不需要重写移动、相机或战斗代码。

**面试表达**

“我把 Input System 当作设备层，而不是让角色代码直接读取键盘。角色控制器只消费语义化的移动和视角向量，所以键鼠与手柄能共用同一套玩法逻辑，也提前为按键重映射留出了边界。”

### 2. 相机与角色水平朝向相互影响，导致镜头自行旋转

**问题**

早期方案让角色与 FreeLook 共享水平朝向。它在直线奔跑时容易出现镜头跟随角色自行旋转；斜向行走后转动鼠标时，角色和镜头还会产生重复旋转或角度累积。问题本质是同一个 Yaw 同时被相机输入、角色移动和 Cinemachine Follow 目标旋转多个来源写入。

**排查思路**

- 分别检查 Player Transform、Animator Root Motion 和 FreeLook X Axis，确认根节点没有 X/Z 倾斜、Root Motion 已关闭。
- 对比“鼠标驱动相机 Yaw”“角色转向”“FreeLook 跟随目标旋转”三个链路，定位到是控制权重叠，而非单纯的灵敏度问题。
- 将镜头转动和角色转动拆开验证：只有一个模块可以在某一时刻写入某个朝向。

**处理**

- 探索状态改为相机相对移动：将 Main Camera 的前方和右方投影到水平面，计算实际移动方向。
- 角色仅在有移动输入时，以平滑 Yaw 面向实际移动方向；鼠标和右摇杆只修改 FreeLook 视角。
- 将 FreeLook `Binding Mode` 配为 `WorldSpace`，防止 Follow 目标旋转隐式带动镜头水平朝向。
- 使用纯 Yaw Quaternion 回写角色旋转，防止未来资源或组件引入 X/Z 倾斜。

**工程收益**

明确了朝向控制权：探索状态下相机由 Look 输入控制、角色由移动方向控制；锁定状态再由锁定模块接管。该规则避免了多个系统同时修改 Transform 的隐性耦合。

**面试表达**

“这个问题不是调参数能解决的，而是朝向控制权没有收敛。我把相机和角色的 Yaw 写入职责分开，再用 Cinemachine 的 WorldSpace 绑定消除 Follow 目标旋转的隐式影响，最终稳定了探索移动手感。”

---

### 3. 探索与战斗对动画方向的语义不同

**问题**

项目具有未持武器和持武器两套八方向 Blend Tree。探索状态希望角色向相机左方移动时转身并播放前进行走/奔跑；战斗和锁定状态则需要保留左右横移、后退和斜向的八方向动画。如果两种状态直接复用同一组 Animator 参数，动画语义会冲突。

**处理**

- 探索状态：将相机相对输入转换为世界移动方向，角色平滑转向；传入 Animator 的移动参数规范化为前进向量，因此所有探索方向都使用前进动画。
- 战斗状态：保留原始二维输入作为 Animator 参数，继续驱动战斗八方向 Blend Tree。
- 将移动计算、角色转向和动画参数组三件事拆开：
  - 移动方向决定 CharacterController 位移；
  - 朝向决定角色模型面向；
  - 动画参数表达当前状态应该播放哪类动作。

**工程收益**

不需要复制动画状态机，也避免用 Animator 当前状态反推玩法状态。后续加入冲刺攻击、后撤步或锁定侧移时，可以只扩展状态规则，而不破坏探索移动。

**面试表达**

“我没有把输入方向直接等同于动画方向。探索状态的 A 键语义是‘转向相机左方后前进’，战斗状态的 A 键语义是‘保持面向并左移’，所以我在控制器层区分了移动、朝向和动画参数。”

---

### 4. 战斗奔跑规则与探索奔跑规则不能混用

**问题**

探索模式为了支持任意方向奔跑，冲刺条件被定义为“按住 Sprint 且存在任意移动输入”。直接复用该条件后，战斗状态出现 `Shift + A/D/S` 也进入奔跑速度和奔跑动画的问题，破坏了战斗横移节奏。

**处理**

- 拆分 `HasExplorationRunInput` 与 `HasCombatRunInput`。
- 探索奔跑保持“任意有效方向输入即可奔跑”。
- 战斗奔跑限定为：Sprint 按下、前向输入超过阈值、横向输入低于 `combatRunLateralThreshold`。
- 默认横向死区为 `0.1`，键盘可严格限制为纯 W，手柄仍允许少量摇杆误差。

**工程收益**

将“冲刺按钮是否按下”和“当前状态是否允许以该方向冲刺”分离。战斗、探索、锁定、负重或受伤等未来状态都可以独立定义冲刺策略，而不是不断修改一个全局布尔条件。

**面试表达**

“我遇到过探索规则泄漏到战斗状态的问题。修复不是在动画层强行关掉奔跑，而是在移动规则层把探索和战斗的冲刺判定拆开，并给手柄横向输入留了可配置死区。”

---

### 5. 从双虚拟相机切换改为单 FreeLook 的状态化构图

**问题**

最初使用探索 FreeLook 和战斗 Virtual Camera 两套相机，通过 Priority 切换。实际调试中需要维护两套距离、碰撞、Look At、切换过渡和场景/预制体引用；持武器但未锁定时切换镜头的收益有限，却带来了突跳和配置成本。

**处理**

- 保留单一 `CinemachineFreeLook` 作为唯一虚拟相机。
- 持武器、攻击和普通战斗不再切换相机。
- 锁定时才临时改变同一台 FreeLook 的构图：
  - `LookAt` 切换为玩家与目标之间的运行时中点目标；
  - 水平轴平滑对齐玩家到目标方向，使镜头位于玩家后方；
  - 根据玩家到目标距离增加 Orbit Radius，并限制最大额外距离；
  - 解锁时恢复 LookAt 为 Player 和基础半径。

**工程收益**

用“同一相机的状态化参数”代替“多相机对象切换”，降低了状态数量和场景配置复杂度。锁定构图仍有扩展点，但普通战斗不再承担不必要的相机切换风险。

**面试表达**

“我一开始采用双相机切换，后来发现这把简单问题变成了引用和过渡问题。最终改为单 FreeLook，通过锁定状态调整 LookAt、水平轴和 Orbit 距离。这样保留了战斗构图能力，也把常规移动的镜头稳定性做得更好。”

---

### 6. 锁定镜头既要同框，也要处理墙体遮挡

**问题**

锁定时仅看向目标会让玩家落在画面边缘；仅看向玩家又会丢失敌人信息。目标距离变化时固定镜头半径也无法保证双方同框。与此同时，角色背后有墙体时，相机还会穿墙或突然贴脸。

**处理**

- 创建运行时 `Lock LookAt Target`，位置平滑跟随玩家与目标的水平中点。
- 锁定距离根据双方水平距离动态增加，使用安全余量、最大额外半径和插值速度限制拉远幅度。
- 从玩家观察高度向实际相机方向执行 `SphereCastAll`，忽略 Player 自身碰撞体；命中环境时快速收缩 Orbit Radius，无遮挡时慢速恢复。
- 将“锁定额外距离”和“防穿墙缩放”分层计算，避免两套逻辑彼此覆盖。

**工程收益**

相机构图、距离策略和防穿墙检测成为独立步骤，便于后续增加目标切换、目标权重、透明遮挡和 Boss 大体型补偿。

**面试表达**

“锁定相机不是简单把 LookAt 指向敌人。我把它拆成构图目标、动态距离和遮挡收缩三层：中点保证双方同框，距离根据目标远近调整，SphereCast 负责防穿墙。”

---

### 7. 一次性编辑器工具的资源路径失效

**问题**

开发初期为快速完成 Input、Animator 和相机对象配置，编写了仅服务当前阶段的编辑器工具。之后 Player 预制体目录调整，工具中的硬编码路径仍指向旧位置，导致 `LoadPrefabContents` 抛出路径不存在异常。

**处理与反思**

- 对确认不会复用的一次性工具进行了删除，避免未来误执行造成更多副作用。
- 若后续确实需要长期维护工具，应使用 Asset GUID、AssetDatabase 查询或可配置字段，不依赖硬编码路径。
- 工具应区分“迁移脚本”和“长期生产工具”：前者完成后随版本移除；后者才需要做路径兼容、幂等性、Undo 和异常处理。

**面试表达**

“我使用过编辑器工具加速原型搭建，但也遇到了资源重组后硬编码路径失效的问题。这个经历让我把一次性迁移工具和长期工具分开管理：一次性脚本完成任务后删除，长期工具则必须使用稳定资源标识并保证可重复执行。”

## 三、当前架构边界

```text
Input System
    -> InputManager                 输入语义、死区、设备差异
    -> PlayerController             移动规则、角色朝向、动画参数
    -> CameraModeController         FreeLook 输入、锁定构图、碰撞收缩
    -> LockOnController             目标筛选、锁定/解锁事件
    -> PlayerAnimation              Animator 参数与表现
```

- `LockOnController` 通过 `LockOnTargetChangedEvent` 广播锁定目标。
- `PlayerController` 只根据事件决定锁定时面向目标，不直接管理镜头对象。
- `CameraModeController` 只消费锁定事件来调整镜头构图，不决定攻击、装备或动画状态。
- `PlayerAnimation` 只接收移动参数和状态标志，不承担实际位移或锁定判定。

这种划分属于事件驱动的表现层协作：对象之间通过类型事件传递状态变化，而非相互持有大量组件引用。

## 四、2 分钟项目讲述示例

“我在第三人称动作 RPG 原型中负责了玩家操控和镜头系统。最初最大的困难不是单个功能，而是相机、角色朝向、动画和锁定状态之间会互相影响。比如我曾让角色和镜头共享水平朝向，结果斜向移动或奔跑时会出现镜头自行旋转，因为相机输入、角色移动和 Cinemachine Follow 都在改同一个 Yaw。

我把控制权重新划分：探索时镜头只由鼠标或右摇杆控制，角色根据相机相对的移动方向平滑转向；战斗时保留八方向 Strafe 动画，锁定时角色再由目标朝向接管。输入层通过 Input System 和 InputManager 统一键鼠与手柄，移动层再按探索和战斗分别处理冲刺规则。

相机方面我从双虚拟相机切换改成一台 FreeLook 的状态化构图。普通状态保持自由镜头，锁定时才把 LookAt 切到玩家和敌人的中点、按距离拉远，并通过 SphereCast 防穿墙。这样减少了 Priority 切换和两套相机配置带来的跳变问题，也给后续目标切换、镜头震动和技能镜头留下了扩展空间。”
